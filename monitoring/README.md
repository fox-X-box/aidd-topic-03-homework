# Персональный мониторинг акций

Новая функциональность задания №4, отсутствовавшая в исходном проекте.

1. Авторизованный пользователь создаёт именованные персональные списки наблюдения. Название уникально внутри пользователя; другие пользователи могут иметь одноимённые списки.
2. В список добавляются акции с положительной целевой ценой (до 9 знаков после запятой, в валюте акции) и условием `цена ≥ цель` либо `цена ≤ цель`.
3. Каждое новое принятое наблюдение рыночной цены передаётся в `evaluate_alerts(share, price, observed_at=None)`. Равенство порогу считается выполнением условия. Сервис возвращает количество созданных уведомлений.
4. При первом выполнении условия система создаёт уведомление в личном встроенном inbox, сохраняя цену, время, тикер, валюту, направление и цель. Email, SMS и внешний push не требуются и не отправляются.
5. Одно правило срабатывает один раз за всю свою жизнь. Повторные и параллельные обновления цены не создают дубликаты: используются транзакционная блокировка правила и уникальная связь уведомления с правилом. Для повторного уведомления создаётся новое правило.
6. Пользователь просматривает и отмечает прочитанными только собственные уведомления. Нельзя читать, пополнять или удалять чужие списки и правила, а также менять статус чужого уведомления.
7. Удаление списка/правила выполняется только POST с CSRF. Уже доставленные уведомления сохраняются; ссылка на удалённое правило становится пустой.
8. Без новых котировок уведомления не создаются. При отсутствии API-токена поведение можно проверить воспроизводимыми demo-котировками, переданными в общий сервис записи рыночных цен.

## Архитектура

`Watchlist(owner, name)` → `WatchRule(share, direction, target_price)` → однократное `Notification`. HTTP CRUD работает с ограниченными по владельцу queryset. Внешние котировки обрабатываются общим сервисом рынка, который вызывает `monitoring.services.evaluate_alerts`. Сам monitoring не обращается к внешним поставщикам.

Уведомления пагинируются по 50. Неизвестные/чужие объекты отвечают 404. Сервис отвергает неконечные, неположительные, слишком большие цены, избыточную точность и время без часового пояса.

## Проверки

`python manage.py test monitoring` проверяет включённые границы условий, одноразовость после повторного входа цены в диапазон, недопустимые цены/цели, сохранение уведомлений после удаления правила, повторную постановку, работу HTML, недопустимость GET-мутаций и изоляцию владельцев. На PostgreSQL также выполняется параллельный тест двух обновлений; на SQLite он помечается skipped, так как SQLite не предоставляет блокировку строк `SELECT FOR UPDATE`.
