# Симулятор стратегий

1. Авторизованный пользователь создает правило в собственном виртуальном портфеле: акция, положительное количество (до 8 знаков после запятой), положительный порог цены (до 9 знаков), покупка либо продажа.
2. Покупка срабатывает при первой новой цене ≤ порога; продажа — ≥ порога. Валюта акции должна совпадать с валютой портфеля. Реальная заявка брокеру не отправляется.
3. Исполнение использует фактически полученную цену, общий атомарный сервис виртуальных сделок и уникальный ключ `strategy:<id>`; повторная обработка котировки не создает вторую сделку.
4. Стратегия однократная. Успех либо бизнес-ошибка закрывает правило и создает единственную запись журнала с временем котировки, ценой, ссылкой на сделку или причиной отказа. Для нового запуска создается новое правило. Ожидающее правило можно отменить POST-запросом.
5. Пользователь видит только свои правила и журнал. Создание правила для чужого портфеля отклоняется. Изменение состояния защищено CSRF.
6. Для оценки результата продажи показывается реализованная прибыль сделки. Для покупки показывается **гипотетическое** изменение стоимости первоначального объема `(текущая цена − цена исполнения) × количество`, как если бы объем продолжали держать; это не фактическая прибыль после последующих продаж. Для каждого результата выводится процент от стоимости приобретения. Для продажи знаменатель процента — себестоимость проданного объема, а не выручка. Нулевая текущая цена покупки дает −100%, отсутствие текущей цены — неизвестный результат. Это не бэктест и не доходность всего портфеля; результаты разных валют не объединяются.
7. Нехватка денег, акций или несовпадение валюты фиксируются как отказ. Неожиданные ошибки инфраструктуры пробрасываются вызывающему обработчику и не маскируются успешным исполнением.

Точка интеграции: `strategies.services.evaluate_strategies(share, price, observed_at=None)` после сохранения новой котировки. Уведомления и журнал не генерируются на основании устаревших данных при простом просмотре страницы. Данные сохраняются в PostgreSQL/SQLite через миграции Django. Проверки гонок при исполнении используют блокировки PostgreSQL; SQLite предназначена для локального однопроцессного режима.

Вход обработчика котировок проверяется до исполнения: цена конечная, положительная, меньше `10^15`, не более 9 знаков после запятой; время — datetime с часовым поясом. Правила, удаленные конкурентно до блокировки, пропускаются.
